# `nova test`, `@` attributes and `std/test` — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let Nova code be tested in Nova — `@test` functions, discovered by the compiler and run one-process-each by `nova test`, asserting with `std/test`.

**Architecture:** Four layers. `@name(args)` attribute syntax lands in lexer/AST/parser; the resolver validates placement and collects `@test` functions in source order; a synthesized HIR `main` dispatches to one test by index, read from an environment variable through a new `STD_ONLY` builtin; `nova test` compiles once and runs the binary per test, distinguishing a Nova panic from a hard trap by **stderr**, not exit code. MIR, monomorphization and both backends are untouched.

**Tech Stack:** Rust (nova-lexer, nova-ast, nova-parser, nova-resolver, nova-mir, nova-runtime, nova-driver, nova-cli), Nova (`std/test`), `assert_cmd` e2e fixtures.

**Spec:** `docs/superpowers/specs/2026-08-05-nova-test-design.md`. **Read §1.1's probe table before starting** — twelve measured rows, two of which were closed after approval and one of which falsifies `nova-spec/20-STDLIB.md` §11's own example.

**Base:** `main` at `73d0a63`. Create branch `nova-test`.

## Global Constraints

Every task's requirements implicitly include this section.

- **`cargo build --workspace` BEFORE `cargo test`.** `cargo test` does not regenerate `nova-runtime`'s staticlib, so ~25 `*_build_standalone` tests fail with a bogus MSVC unresolved-symbol error otherwise. Measured; CI shares the hole.
- **`--no-fail-fast` is mandatory** on `cargo test --workspace`, or cargo abandons later test targets on the first failure and under-reports.
- **A zero-match `cargo test <filter>` EXITS 0.** Check the `running N tests` line is non-zero before treating a filtered run as evidence. This has produced false "verified" claims twice on this project.
  - **A specific instance, measured on this branch:** `cargo test -p <crate> --lib --exact <bare_fn_name>` matches **zero** tests and exits 0. `--exact` requires the fully-qualified path — `check::tests::<name>` — so the bare name silently selects nothing. Task 2's implementer hit this on eight consecutive tests and caught it only from the `running 0 tests` line.
  - Also measured: **no single substring filter selects all of Task 2's tests**, because their names are not uniform (`an_unknown_attribute_*`, `test_on_a_*`, `test_before_a_*`). Verify by exact qualified name, or by the unfiltered target count against a known baseline.
- **`cargo test --workspace` rebuilds `nova.exe`**; `cargo test -p <crate>` does not. `std/` is embedded via `include_str!`, so after editing `std/` or reverting a mutation, run `cargo build --workspace` before any `nova run`/`nova check` probe. This cost agents real findings on two previous branches, in both directions.
- **Baseline: 640 tests passing, 0 failed; clippy `-D warnings` and `cargo fmt --check` clean; 15 gate configurations green** (5 fixtures × run/build/GC-stress). Take your own baseline; do not trust a number written here.
- **Nova language limits, all measured:** no `loop` (use `while true`); no tuples; no references; `///` lexes to `Token::DocComment` but the parser does not attach it to anything; `(self.f)(x)` is `E0014` — bind `let g = self.f` first; a record literal cannot be a `for` iterable; an empty `Vec::new()` needs a type annotation; `Option<Int>` has no `Display`; record-literal field order matters when a field type names a projection.
- **A monomorphization-seam test is only as good as the `MirTy` classes it instantiates at.** `mir_ty` (`crates/nova-mir/src/lib.rs:443-452`) maps `Int` *and* `Char` to `MirTy::I64`, and `String`/`Fn`/`Sum`/`Record`/`Array` to `MirTy::Ptr` = `i64` on x86-64. Only `Bool` (`I8`) and `Float` (`F64`) are disjoint from both, and **`Float` is the strictly stronger of the two** because it crosses register banks while `Bool`'s 0/1 survive an `I64` confusion intact.
- **Diagnostic codes in use:** `E0001`, `E0002`, `E0010`–`E0016`, `E0020`–`E0022`, `E0060`, `E0070`–`E0081`, `E0403`, `E0428`, `E0601`, `E0900`, `E0902`. This plan adds `E0082`–`E0085`. `E0086` onward stays free.

A test over only *passing* inputs is the worst case: `assert_eq(1, 1)` succeeds even if the comparison never runs.

**Files:**

- Modify: `crates/nova-parser/src/grammar.rs:234` (`try_parse_item`)
- Test: `crates/nova-parser/tests/parser_tests.rs`

**Measured before dispatch — the existing test helpers cannot express these tests.** `crates/nova-parser/tests/parser_tests.rs` has only `parse_file(name, source) -> (bool, usize)` and `parse_fixture(fixture) -> (bool, Vec<String>)`; neither returns the parsed `File`, so no existing helper can inspect `f.attrs`. Add one thin helper beside them that returns the AST and the errors, and use it for all six tests. `grammar.rs`'s real signatures are `expect(&mut self, tok: &Token, ctx: &str)` and `parse_ident(&mut self, ctx: &str)`, and there is no `prev_span` — the code below uses them correctly; do not "fix" it back.

**Interfaces:**
- Consumes: nothing.
- Produces: `nova_ast::item::Attribute { name: Spanned<String>, args: Vec<Spanned<String>>, span: Span }`, and `attrs: Vec<Attribute>` readable on `Function`, `Record`, `TypeDecl`, `TraitDecl`, `ImplBlock`, `ConstDecl`. Task 2 validates them; nothing else reads them.

**Why `attrs` on all six and not just `Function`.** `@test` only applies to functions, so `Function` alone would do for this increment. But `@derive(Copy, Clone)` is spec-mandated on *type declarations* (`nova-spec/12-TYPESYSTEM.md:199`), so attributes on records are coming regardless, and the resolver needs to *see* a misplaced `@test` in order to report `E0083` with a span — a parser-level rejection would have to invent a `P`-code the spec does not assign. Adding the field once to all six avoids touching the same structs twice and keeps the diagnostic where the spec puts it.

- [ ] **Step 5: Parse them**

In `grammar.rs`, add a method and call it as the first line of `try_parse_item` (`:234`), **before** `parse_visibility()`:

```rust
    /// Parse zero or more leading `@name` / `@name(a, b)` attributes.
    ///
    /// Placement is not checked here — an attribute on a record parses and is
    /// kept, so the resolver can report `E0083` with a span. The parser's job
    /// is syntax; the known-attribute set is Task 2's.
    fn parse_attributes(&mut self) -> Vec<Attribute> {
        let mut attrs = Vec::new();
        while self.peek() == &Token::At {
            let start = self.peek_span();
            self.advance();
            let Some(name) = self.parse_ident("in attribute name") else { break };
            let mut args = Vec::new();
            if self.peek() == &Token::LParen {
                self.advance();
                while self.peek() != &Token::RParen && !self.is_at_end() {
                    let Some(arg) = self.parse_ident("in attribute arguments") else { break };
                    args.push(arg);
                    if self.peek() == &Token::Comma {
                        self.advance();
                    } else {
                        break;
                    }
                }
                self.expect(&Token::RParen, "in attribute arguments");
            }
            let span = start;   // widen only if the file has a span-join helper;
                                // there is no `prev_span` in grammar.rs.
            attrs.push(Attribute { name, args, span });
        }
        attrs
    }
```

Then thread the result into whichever item is parsed. Use the existing helpers — `peek_span` (`grammar.rs:85`), `expect` (`:116`), `parse_ident` (`:2358`) — rather than inventing new ones. Those three are the only ones this needs and all three were verified to exist with the signatures used above.

**The `break` on a missing identifier is deliberate and must not become an unconditional `advance()`.** `parse_file`'s loop (`:194-232`) guarantees progress by checking `self.pos` before and after `sync_to_item_boundary`, and that guarantee exists because adding `RBrace` as a sync stop made a two-line file hang `nova check` for 15 seconds. Returning without consuming lets that checked-progress path do its job; consuming blindly would turn one bad item into two.

- [ ] **Step 4: Implement validation and collection**

In the resolver's item walk, for every item, validate its `attrs`:

- name not in `{"test"}` → `E0082`, message naming the attribute and listing the known set. **Do not silently ignore it.** This project's most-repeated defect is "parses, then enforces nothing" — record-parameter bounds, impl-level `const`s, `pub` on methods, record field visibility. - an argument other than `should_panic` → `E0085`.
- otherwise push a `TestFn` in walk order.

Four separate codes rather than one catch-all, because `E0900` already demonstrates the cost of a catch-all: it reports "not supported yet" when the real fault is specific, and Task 2 of the previous increment had to work around exactly that.

```nova
// std/test — assertions for `@test` functions.
//
// Seeded ONLY when compiling under `nova test` (see `STD_TEST_MODULE`), not
// into every program. A top-level `pub fn assert` in an always-embedded module
// would be glob-imported and take the names `assert`, `assert_eq` and
// `assert_ne` in every module of every program — the same hazard that made
// `join` hang off the separator (`",".join(parts)`) rather than being a free
// function. The cost is that `assert` is unavailable in ordinary code; `panic`
// already serves that need.
//
// Failure is `panic`, which aborts with exit non-zero and `nova: panic: ...` on
// stderr. That is the "panicked" outcome `nova test` looks for, and it is why
// there is no `assert_throws` here: catching a panic needs unwinding, and
// `nova_rt_panic_str` calls `std::process::abort()`. `@test(should_panic)` is
// the supported way to assert that something panics.

pub fn assert(cond: Bool, msg: String) {
    if !cond {
        panic("assertion failed: ${msg}")
    }
}

pub fn assert_eq<T: Eq + Debug>(a: T, b: T) {
    if a.ne(b) {
        panic("assertion failed: ${a.dbg()} != ${b.dbg()}")
    }
}

pub fn assert_ne<T: Eq + Debug>(a: T, b: T) {
    if a.eq(b) {
        panic("assertion failed: ${a.dbg()} == ${b.dbg()}")
    }
}
```

This signature was **measured before planning** (spec §1.1): a free generic fn with two bounds, calling `ne` from one and `dbg` from the other, compiles and runs at `Int`, `Bool` and `String`. No free function in std had two bounds before, so it was unprecedented — hence the probe.

    // I64 and every heap type to Ptr, so only Bool (I8) and Float (F64) are

}

- [ ] **Step 2: Implement the runner**

Compile once via `build_test_binary`. Enumerate by running with no index. Filter by substring on the name (`nova-spec/40-TOOLING.md:20`). For each selected test, run with `NOVA_TEST_INDEX=i` and classify:

```rust
enum Outcome { Passed, Panicked(String), Trapped(i32) }
```

- exit 0 → `Passed`
- nonzero **and** stderr contains `nova: panic:` → `Panicked(message)`
- nonzero **and** no such line → `Trapped(code)`

**Classify on stderr, not the exit code.** 127 and 132 were measured on Windows through Git Bash, and the mapping from `abort()` to an exit code is platform- and shell-dependent. `nova: panic:` is emitted by `nova_rt_panic_str` itself, so it is the portable signal; the exit code only says whether the run was clean.

`@test(should_panic)` inverts **only** `Panicked` → pass. `Trapped` is a failure whether or not `should_panic` is set, and the report must say "trapped", not "failed", so the distinction survives into what a human reads.

Exit nonzero if any test failed. Print one line per test and a summary. **Do not print a count of anything you did not measure** — enumerate what ran.
