# Seeded `mix64` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Seed `Int`, `Bool` and `Char` hashing so those keys resist a precomputing attacker, closing the third of the gate claim's three exclusions and only that one.

**Architecture:** `mix64` is not touched — it stays unseeded, canonical, in Nova, so the fixture's canonical-splitmix64 assertion keeps testing the same function. The three `Hash` impls seed their **input**: `mix64(self ^ int_hash_seed())`. One new nullary intrinsic supplies the seed from its own `OnceLock` draw, separate from `str_hash_seed`.

**Tech Stack:** One new `STD_ONLY` builtin over a runtime function (Rust), three one-line edits in `std/core/lib.nova`, a rewritten golden fixture, and a cross-process test in `crates/nova-cli/tests/run_tests.rs`. No new dependency, no trait change, no new ADR.

**Spec:** `docs/superpowers/specs/2026-08-28-seeded-mix64-design.md`

**B. The "two independent keys" claim is retracted, and it stands at both of
the sites named here.** Task 1 Step 5's proposed doc comment ends "Two
`RandomState::new()` calls give two independent keys". Task 1 Step 6's proposed
test comment says "Two independent `RandomState::new()` calls are what prevent
that". Both are false. The second wraps across the `//` gutter, and a reader
who corrects the doc-comment site alone leaves it standing.

Measured from `std`'s source: `RandomState::new()` caches one 128-bit OS draw
per THREAD in a `thread_local!` cell, hands out `(k0, k1)`, and stores back
`(k0 + 1, k1)`. Two calls on one thread therefore share `k1` exactly and differ
in `k0` by the number of calls between them, and `std`'s own comment says that
increment exists to vary `HashMap` iteration order rather than to make keys
independent. Whichever thread first reaches each `OnceLock` supplies its draw
and neither initialiser pins a thread, so the two seeds can also come from two
separate OS draws; the shared-`k1` case arises only when one thread initialises
both.

What the separate call buys is that the two seeds DIFFER, effectively
certainly. Whether recovering one yields the other rests on the keyed hash's
behaviour under a RELATED KEY, and this increment does not verify that. The
shipped argument is `int_hash_seed`'s doc comment in
`crates/nova-runtime/src/lib.rs`; follow it rather than this summary.

Two things sharpen it. It was measured, not argued: a seed function defined as
`str_hash_seed().wrapping_add(1)` passes every test in the pair Step 6
proposes, so those tests pin that the two seeds differ and nothing past it. And
the shipped `int_and_str_hash_seeds_are_drawn_separately` records that limit in
its own comment rather than repeating the claim.

**C. Task 1 Step 5 prescribes an ABI this branch rejected.** It gives the
export as `pub extern "C-unwind" fn nova_rt_int_hash_seed() -> i64` and
justifies it: "`C-unwind` follows `nova_rt_time_now_nanos`, the closest
existing function in shape". The shipped export is plain `extern "C"`, and the
justification does not hold either.

The reasoning that decided it, from the shipped doc comment on
`nova_rt_int_hash_seed` — read that rather than this precis.
`crate::task::PollFn`'s doc closes its constraint block by saying the
permission `"C-unwind"` grants exists for that module's Rust-side entry points
and not for compiled Nova frames; once `std/core`'s three `Hash` impls call
this, its callers are compiled Nova frames. The panic is real rather than
hypothetical: `get_or_init` runs `RandomState::new`, which draws OS entropy on
the first call, and `std` panics when that draw fails — unconditionally on
Linux and on the `getrandom`/`getentropy` platforms, and under a `debug_assert`
on current Windows, which is this project's gate. So `(0).hash()` inside an
`async fn` body puts that first call inside a generated poll function, which
carries no landing pads. Plain `"C"` escalates such an unwind to an abort,
making the prohibited case structurally impossible instead of resting on the
panic not happening. `nova_rt_str_hash` makes the same `RandomState::new` draw
through the same `OnceLock` and is plain `"C"`, which makes it the precedent
rather than `nova_rt_time_now_nanos`.

"The closest existing function in shape" was measured false. The non-`unsafe`
nullary exports returning `i64` that use `C-unwind` are
`nova_rt_log_config_level` and `nova_rt_log_config_to_stderr` in
`crates/nova-runtime/src/log.rs`, and `nova_rt_time_now_nanos` and
`nova_rt_time_now_epoch_nanos` in `crates/nova-runtime/src/time.rs` — so shape
gives a tie among those rather than a closest match, and
`nova_rt_test_selector` in `crates/nova-runtime/src/lib.rs` already carries
that exact signature under plain `"C"`. Reasoning from a neighbouring family's
ABI is the inference `nova_rt_float_fixed`'s doc warns against.

The residual, recorded without resolving it: each of those `log` and `time`
readers is reached from compiled Nova frames too and still uses `C-unwind`. By
the reasoning that decided this function, each is the same question with a
different panic profile. That divergence is pre-existing, was deliberately left
alone here, and wants a decision somewhere other than a doc comment.

**F. The canonical-vector line is misclassified, and the premise is
load-bearing at each of the sites named here.** They are the **Architecture**
line in this file's header; Task 2 Step 2's instruction to extend `mix64`'s own
note; Task 2 Step 3's keep-unchanged roster, which reads "`splitmix64 canonical
x1=true x3=true`, which passes because `mix64` is untouched"; and the closing
**Notes for whoever executes this**, under "Why `mix64` is not touched".

The fixture line does not call `mix64`. It called `.hash()`, and once the impls
are seeded that expression is `mix64(x1 ^ seed)`, which equals the pinned
constant only at seed 0. Leaving `mix64` untouched preserves the function and
not the assertion.

What shipped, in `tests/runtime/hash.nova`: the fixture recovers the seed and
cancels it. It carries its own `mix64_inv`, sets `let s =
mix64_inv((0).hash())` and asserts `((-7046029254386353131) ^ s).hash()`
against the pinned constant. Since `(x1 ^ s) ^ s` is `x1`, both halves print
`true` at every seed and the golden line `splitmix64 canonical x1=true x3=true`
survives byte-identical — for a reason this plan does not state anywhere: not
that `mix64` was left alone, but that `mix64` is a bijection and `(0).hash()`
is `mix64(seed)`, so ordinary Nova can recover the seed and cancel it before
asserting. The inverse is written out in the fixture because ADR 0005 makes
`mix64` module-private to `std/core` on purpose, so a fixture cannot call it.

The closing note's "Keeping `mix64` canonical and seeding its callers preserves
that assertion testing the same function" is retracted in that second half: the
route the design did take destroyed the assertion as written, and it was
rewritten rather than preserved. Its first half — that seeding `mix64` in place
would have destroyed the line — is true and is not the point; both routes
required the line to change.

How the misclassification was reached is the reusable part. The design was
verified by compiling the three seeded impls with a literal `0` standing in for
the seed call and finding the golden byte-identical, which the **What is
verified and what is not** section records as verified. At seed 0 the XOR is
the identity, so that probe reproduces the old output BY CONSTRUCTION: it
cannot distinguish "invariant over every seed" from "identical at seed 0". The
lines Step 3 files as invariant that really are invariant are so for reasons
this one does not have: `bound` and `char/int agree` compare two hashes that
both carry the seed, so it cancels; the `Int`, `Bool` and `Char`
`same=`/`diff=` halves and `h(0) != h(-1)` follow from `mix64` being injective
at every seed; and the complement-collision count is the theorem Step 3's next
paragraph states. Neither reason covers this line, and neither covers `buckets
reached 8 of 8`, which entry G takes up. (The two `String` relations are a
third case the shipped fixture header sets out: `str_hash` carries its own
seed, so their `diff=` halves are seed-dependent at a magnitude around 2^-64
and are left unbounded on purpose.) This one was classified from the probe
instead of from the route its expression takes. The shipped fixture header
states the trap under "A NOTE ON HOW NOT TO CHECK THIS FILE".

**G. `buckets reached 8 of 8` is a random variable, not an invariant.** Task 2
Step 3 files it under "Keep unchanged, invariant over every seed tested" as
"`buckets reached 8 of 8 (identity hashing would reach 1)`, measured min 8 and
max 8", and the paragraph rejecting a largest-bucket bound says it "asserts
that directly and is invariant".

The statistic counts distinct buckets among the 64 multiples of 8 masked into 8
buckets. Recomputed here from the exact occupancy distribution over rationals,
`P(some bucket empty)` is 1.554270e-03, about one run in 643 per process; both
`hash_run` and `hash_build_standalone` read that golden, in separate processes,
which is about one run in 322 across the suite. And "measured min 8 and max 8"
is not evidence of invariance: at that rate 1000 draws show no failure about 21
per cent of the time.

What makes this more than an arithmetic slip is that three sentences earlier
the same step refuses a largest-bucket bound because "Even `largest < 56`
flakes at **1.62e-04, about 1 run in 6,169**" — a figure this amendment
recomputes as right. So the flake Step 3 retained is about nine and a half
times more frequent than the one it rejects by name, and it was retained with
no disclosure.

What shipped is a bound: `buckets reached >= 6: true (identity hashing would
reach 1)`, whose false-failure probability is 4.836243e-12, in the same band as
the two derived bounds beside it at 2.37e-11 and 8.41e-10. A bound of at least
7 was rejected at 2.825296e-07, about 336 times the loosest bound already
there, which is two and a half orders. The shipped fixture header said three
and has since been corrected to match, so there is no longer a divergence to
reconcile. Nothing real is lost dropping from 8 to 6: what the line guards
is that hashing is not the identity, and `fn hash(self) -> Int { self }` puts
all 64 multiples of 8 in bucket 0, reaching 1, as does a constant hash. The
shipped fixture header derives all of it, and also records what the loosening
costs — nothing in that file constrains the 8-bucket distribution any more,
only its support.

So Step 3's roster of lines to keep unchanged is governed by the shipped golden
at two of its entries: this one, whose text changed, and the canonical-vector
line of entry F, whose text was kept only by changing the fixture.

**H. Two figures whose labels name a model other than the one computed.** The
sites are Step 3's table column headed "exact probability", Step 3's
largest-bucket rejection, and Step 4's bound. Step 4 gives that bound's
derivation as "`Binomial(32, 1/64)` unioned over 64 buckets gives
8.2686863018e-11, about 1 run in 12,093,819,544". Recomputed here from exact
rationals rendered through `Decimal` rather than a float: with `P` the
single-bucket tail `P(Binomial(32, 1/64) >= 11)`, the union `64 * P` is
8.2686863021e-11 at eleven significant figures, while 8.2686863018e-11 is what
`1 - (1-P)^64` — an independence model, not the sum this label names — rounds
to at eleven. The two agree at ten figures and part at the eleventh, which is
why eleven is the precision the argument uses. The reciprocals of both round to
12,093,819,544, so that figure is not evidence either way. The root record is
`docs/superpowers/specs/2026-08-27-hashdos-resistance-test-design.md`, amended
today for the same figure; the shipped doc comment on
`hashdos_precomputed_int_key_set_does_not_survive_a_new_process` carries the
corrected account.

Step 3's 1.62e-04 has the right value and the wrong kind. It is a sum over the
8 per-bucket tails, which are not disjoint events, so it is a Bonferroni upper
bound on the flake probability rather than that probability. The shipped
fixture labels it as one; this plan does not. The same applies to Step 3's
table column headed "exact probability": each figure there is exact for a model
in which the hashes involved are independent and uniform, and they are not
independent — every one is a deterministic function of a single 64-bit seed, so
at most 2^64 outcomes stand where the model for the 128-key line alone has
256^128. Read each figure as exact for the model, an estimate for the run, and
an upper bound wherever it sums non-disjoint events. These are finite exact
summations — inclusion-exclusion over an occupancy distribution, or a binomial
tail — so "computed rather than sampled" is the accurate phrase and "closed
form" would not be.

```rust
/// The per-process seed for `Int`, `Bool` and `Char` hashing.
///
/// A SEPARATE draw from [`str_hash_seed`], deliberately. If the two shared a
/// value then `(0).hash()` would equal `("").hash()` exactly, since both
/// reduce to [`splitmix64_finalize`] applied to the seed, and recovering
/// either would recover both. Two `RandomState::new()` calls give two
/// independent keys.
///
/// One value for the whole process, for the same reason `str_hash_seed` gives:
/// a `Map` built under one seed and probed under another finds nothing.
fn int_hash_seed() -> u64 {
    static SEED: OnceLock<u64> = OnceLock::new();
    *SEED.get_or_init(|| {
        use std::hash::{BuildHasher, Hasher};
        let mut h = std::collections::hash_map::RandomState::new().build_hasher();
        h.write_u64(0);
        h.finish()
    })
}

/// The per-process seed `std/core`'s `Int`, `Bool` and `Char` hashing XORs
/// into its input before `mix64` runs.
///
/// **Nova code can recover this value in one call**: `(0).hash()` is
/// `mix64(0 ^ seed)`, which is `mix64(seed)`, and `mix64` is an invertible
/// bijection. That is the same shape `("").hash()` already has for the string
/// seed, it follows from ADR 0005's one-shot `Hash` returning a plain `Int`,
/// and the gate claim already declines the adaptive attacker for whom it
/// matters. What the seed buys is precomputation resistance.
///
/// Nullary and takes no pointer, so it needs no `unsafe`; `C-unwind` follows
/// `nova_rt_time_now_nanos`, the closest existing function in shape, so an
/// unwind out of `get_or_init` is defined rather than undefined. Note
/// `nova_rt_str_hash` uses plain `"C"` while also reaching a `OnceLock`; that
/// difference is pre-existing and is not changed here.
#[no_mangle]
pub extern "C-unwind" fn nova_rt_int_hash_seed() -> i64 {
    int_hash_seed() as i64
}
```


```
impl Hash for Bool   { fn hash(self) -> Int { if self { mix64(1 ^ int_hash_seed()) } else { mix64(0 ^ int_hash_seed()) } } }
```

buckets with `hash & (cap - 1)`. Post-XOR — `mix64(x) ^ seed` — leaves the low
bits as `(mix64(x) & mask) XOR (seed & mask)`, which *permutes* buckets and
leaves every colliding pair still colliding. It would look like seeding and buy
nothing. Do not "simplify" it in that direction; Step 6's first mutation exists
to catch exactly that.

## Notes for whoever executes this

**Why `mix64` is not touched.** Seeding it in place would have destroyed
`splitmix64 canonical x1=true x3=true`, which ADR 0005 records as computed from
the algorithm rather than recorded from a run. Keeping `mix64` canonical and
seeding its callers preserves that assertion testing the same function.

**Why the seed comes from a new intrinsic rather than from Nova.** `mix64` is
Nova, and `str_hash("")` is reachable in `std/core` and stable per process — so
seeding without touching the compiler looked possible. Measured, it costs about
950 ns against a 35 to 48 ns baseline, because it allocates a `String` per
hash. A runtime call costs about 15 ns and a GC allocation about 900 ns. That
separation took three measurements: the first two both allocated, agreed at
about 900 ns, and together supported the wrong conclusion that no route was
viable.

**What this does not buy.** The timing-adaptive adversary stays unclaimed, the
hash stays non-cryptographic, and the seed is recoverable in one call. The
`Int` path ends up exactly as strong as the `String` path, and no stronger.
