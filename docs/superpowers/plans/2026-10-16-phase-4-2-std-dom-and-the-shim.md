# Phase 4.2, "`std/dom` and the shim", Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a program built for WASM builds a page, changes it, and answers
clicks, timers and network replies. std declares its JS functions with
`extern "js"`, which only std may write. The shim holds JS objects in a
table and Nova holds their slots in boxes, which the collector releases.
A closure JS may call is a root of `std/rt`'s table, and each call from JS
is a turn. A task can wait on a token JS settles, which is how `fetch`
awaits. `std/dom` is std's first module outside the prelude: a program
writes `import dom`, natively that is E0092, and the names `dom` and `ui`
are std's. The gate: `tests/dom/counter.nova` counts three clicks under
the fake DOM in `cargo test` on all three systems, and in Chromium in a
new CI job.

**Architecture:**
- **`nova-resolver`:** `$std.dom` in WASM's std, before `$std.rt`, glob-
  imported into no module; `IMPORTED_STD`, so `import dom` falls back to
  std's module, and is E0092 on a target without it; `std/rt`'s names
  glob only into std's modules; `RESERVED_MODULE_NAMES`; two more
  `Builtin::WASM_ONLY`, `closure_word` and `closure_call`.
- **`nova-driver`:** E0093 for a module or dependency `import` finds under
  a reserved name.
- **`nova-pm`:** `dom` and `ui` refused as package names.
- **`nova-hir`, `nova-typeck`:** `ExternAbi { C, Js }` on `ExternFn`;
  `extern "js"` in a std module of a WASM build, with `String` allowed.
- **`nova-mir`:** `ExternDecl::abi`; `MemOp::{ClosureWord, ClosureCall}`;
  `RT_JS_ENTRIES`, the exports a trigger function brings.
- **`nova-codegen-wasm`:** imports for `extern "js"` after the host
  functions and before `abort`; `closure_call` as a `call_indirect`; the
  shim's `js_function` table, each entry guarded; `shim/dom.js`,
  `shim/dom_call.js`, `shim/dom_fetch.js`; the scheduler in `run.js`.
- **`std/dom`:** new. **`std/rt`:** boxes and their registry, the closure
  table, token waits, `rt_call`, `rt_wake`, and `-2`.
- **Tests:** `tests/dom/`, the fake DOM and twelve programs with their
  harnesses; `tests/browser/counter.mjs`; the `browser` job.
- **Records:** ADR 0041, and dated notes.

**Tech Stack:**

- JS for the shim and the tests: ES modules, run by browsers and Node 22.

- Tests: unit tests in `nova-resolver`, `nova-driver`, `nova-typeck`,

- **The patches.** Each task's code is in patch blocks below, each marked
  `<!-- patch NAME -->` and fenced with four backticks. They are the
  prototype's commits, so apply them; do not retype them. From the
  repository's root:

  ```sh
  PLAN=docs/superpowers/plans/2026-10-16-phase-4-2-std-dom-and-the-shim.md   # this file, committed
  block() {
    awk -v name="$1" '
      $0 == "<!-- patch " name " -->" { grab = 1; next }
      grab && /^````diff$/ { inside = 1; next }
      inside && /^````$/ { exit }
      inside { print }
    ' "$PLAN" > "$P/$1.patch"
  }
  patch_block() {
    block "$1" && git apply --check "$P/$1.patch" && git apply "$P/$1.patch"
  }

## Decisions: where this plan settles what the spec leaves open

Each was a ruling while prototyping; each is open to the user's review.
Decisions 2, 3, 5, 6, 7, 9, 10, 11, 13, 14, 16, 17, 19, 21, 24, 25, 26, 27
and 28 differ from a sentence of the approved spec, and decision 29 from
its list of crates.

### The language

1. **`ExternAbi { C, Js }` is `nova-hir`'s, re-exported by `nova-mir`,** so
   the backend names it without a new dependency (`Cargo.lock` unchanged).
   `hir::ExternFn` and MIR's `ExternDecl` gain `abi`. The checker accepts
   `"js"` only when the block is in a std module and the target is WASM;
   anywhere else it is E0900, as before. The backend refuses a C extern
   that reaches it with an error naming it; the resolver's E0090 keeps a
   user's from reaching it.
2. **The JS of each `extern "js"` function is an arrow function in
   `shim.rs`'s `js_function(name)`,** where the host functions' JS already
   is. `shim/dom.js` holds the handle table, `novaPanic` and `guard`;
   `shim/dom_call.js`, the calls from JS; `shim/dom_fetch.js`, `fetch`'s
   token. Each part is added only when the module imports a function that
   needs it. Spec §3.1 and §8 put each function's JS in `shim/dom.js`.
3. **`std/rt` declares three `extern "js"` functions of its own,**
   `host_release`, `host_handles` and `host_done`, named for the runtime,
   not with `dom_`. Spec §4.1 calls the release `handle_release`, and §6.2
   names every JS function with a `dom_` prefix.
4. **Every `extern "js"` function is wrapped in `guard(name, f)`.** A JS
   exception becomes `nova: panic: std/dom: <name>: <kind>: <message>`; a
   Nova panic, a trap or a stack overflow from Nova code that `f` called
   passes through. If the program ended while `f` ran, by a panic in a
   listener that a browser called and kept, `guard` throws a Nova panic so
   the Nova code that called `f` unwinds too (spec §5.3 leaves this open).

### Handles

5. **A forged `Element` reads the word at its box's address.** A box of 0,
   or any word that is not a live handle, is §4.1's panic; an address
   outside memory traps. A word that holds a live handle reaches that
   handle's object, one the program's own `std/dom` calls put in the
   table. Spec §4.1 and §6.1 say using a hand-built record is the panic,
   "and nothing worse". A tag in the box could not stop a value built to
   pass it, since a program can read its records' fields; what the table
   holds bounds what a forged value reaches.
6. **`std/rt`'s public functions are std-internal.** `STD_INTERNAL`
   (`$std.rt`) globs into std's modules alone, so `std/dom` calls
   `rt_handle_box`, `rt_handle_id`, `rt_closure_register`,
   `rt_closure_release` and `rt_task_host_future` as functions, and a
   user's module cannot name them (`std_rts_functions_are_std_internal`).
   Spec §7.1 reaches the host future "through a routed builtin".
7. **A token is a handle of the shim's one table,** boxed as a node is and
   released by the collector; the wait object holds `done`, then `status`,
   `ok` and `body`, or `error`, which `dom_fetch_*` read. A park on a token
   holds it negated, where a park on a task holds its id plus 1, so the
   sign tells them apart. Spec §7.1 keeps "a table of pending waits, as it
   keeps handles", has `fetch` free its token, and marks a token's park
   "with a flag".
8. **The state words: 88 the handle registry, 96 the closure table.** Each
   is a 24-byte leaf block, made at first use: a leaf table's address,
   the entries used, and the capacity, which doubles. The registry's
   entries are (box, handle) pairs; it marks its block and table, never
   the boxes. 104 to 120 stay free (decision 9).

### Calls from JS

9. **The shim counts the calls in progress, not `std/rt`.** `run()` keeps
   `depth`, and `nova_call(id, arg, outer)` takes a third argument, 1 for
   the outermost call. An inner call runs its handler and returns -2
   without a turn. Spec §5.2 keeps "a depth word in `std/rt`", and gives
   `nova_call(id, arg)`. Only JS knows a call is nested: a listener a
   `dom_*` function dispatches runs inside that function's JS.
10. **A closure entry's id is its index plus 1;** 0 marks a free entry,
    and registration takes the first free one it finds by a scan of the
    entries, where spec §5.1 keeps "a free list". Releasing a free or
    unknown id changes nothing; calling a free entry calls nothing, and the
    call still runs its turn. A listener's JS side is removed before its
    entry is released, and a browser does not call a listener removed
    during a dispatch, so only a forged id reaches a free entry.
11. **`closure_word(f)` is a second WASM-only builtin,** a `fn(Int)`
    closure's address as an `Int`, which `std/dom` passes to
    `rt_closure_register`. Both builtins are in every std module's scope
    on WASM, as 4.1's WASM-only builtins are. Spec §5.1 names
    `closure_call` alone, "which `std/rt` alone may use".
12. **`RT_JS_ENTRIES` in mono:** lowering `rt_closure_register` roots
    `nova_call`, `nova_turn` and `nova_gc_switches`; lowering
    `rt_task_host_future` roots `nova_wake` and the same two. An export an
    `async fn main` rooted already is not added again: twice would make the
    module invalid, as the scheduler program, an `async fn main` with a
    listener, would show. `a_listener_exports_the_call_and_the_turn` checks
    a synchronous `main`'s exports, with a listener and without.
13. **`init` calls `nova_turn` after `main` whenever the module exports
    it,** as 4.1's decision 18 does for an `async fn main`. So a
    synchronous `main` that registers a listener collects at its end when
    a collection is due, and under stress always; the counter's stress run
    shows four collections, `main`'s and three clicks'. Spec §5.2 says
    `main` "is not a call from JS in this sense". A `main` that registers
    nothing exports no turn and never collects (`std_dom_builds_a_page`).
14. **Every shim carries the scheduler.** `run.js`'s `run`, `schedule`,
    `fail` and `end` replace 4.1's `turns()`, so hello world's `app.js`
    grows from 2,313 bytes to 2,822 by `gzip -9`, about 0.5 KB; its
    `app.wasm` stays 2,159. Spec §8 and §10.4 say hello world's size does
    not change. Keeping one path through `init` keeps every program,
    the gate's 94 included, on the code the DOM programs test; the limit
    stays 30 KB.
15. **An `async fn main` imports `host_release` and `host_handles`,**
    since its collector may meet a registry, so its shim carries
    `shim/dom.js` too. A small `async fn main` that sleeps once has an
    `app.js` of 3,758 bytes gzipped, where it had 2,536: the scheduler, and
    about 0.7 KB for the handle table; its `app.wasm` grows from 9,523 to
    10,265, the registry's and the closure table's code in the collector.

### The debug line, the names, the types

16. **The `nova-dom:` line follows every collection of a program with a
    registry or a closure table,** and counts the closures too:
    `nova-dom: collection 3 released 120 handles, 4 live, 1 calls`. The
    live count is the shim's own, `host_handles()`, so it counts slots the
    shim actually frees. Spec §4.2 writes the line only after a collection
    that released handles, without the closures. The handles, counter,
    listeners and timers tests read it.
17. **E0093 is the driver's, when `import` finds a module or dependency
    under a reserved name,** in its own words: "`dom` is the name of a std
    module, so no module may take it: rename" and the module's path,
    labelled "std's module, not this one". Spec §3.2 words it "`dom` is the name of a std
    module; rename this module". A file no `import` reaches is never
    loaded, so it is never refused.
18. **`nova-pm`'s message is "`dom` is the name of a std module, which
    `import dom` names"** (M0003 in a manifest), and its
    `STD_MODULE_NAMES` must equal the resolver's `RESERVED_MODULE_NAMES`,
    which a driver unit test checks.
19. **`Listener { target: Int, kind, entry, js }` and `Timer { slot:
    Entry, js, repeats }`.** `target` holds the target's box address, 0 for
    the window, which keeps the target's handle alive for `remove`.
    `Entry`, a private record, is shared by a timer and its closure, so a
    timeout that fires releases its own entry. Spec §6.1 has `target:
    Element` and `Timer { entry: Int, … }`.
20. **A listener's and a timer's JS side is a handle too,** `js`: the JS
    function, or the timer's id. `remove` and `clear` name it, then zero
    the entry's id where they release it, so doing either again releases
    nothing, though another listener or timer has taken the entry since.
21. **The JS functions are named for the JS they run, with `dom_`:**
    `dom_listen`, `dom_unlisten`, `dom_window_listen`, `dom_query_all`,
    `dom_query_selector_in`, `dom_has_attribute`, `dom_event_*`,
    `dom_clear_timeout` and `dom_clear_interval`, `dom_fetch_*`. Some Nova
    functions call two: `attribute` asks `dom_has_attribute`, then
    `dom_attribute`; `query_selector_all` takes one handle, to a JS array,
    and reads it with `dom_list_len` and `dom_list_item`, the array going
    with its box. Spec §6.2 names each JS function after the Nova one.
22. **`fetch_with` sends the headers as `name: value` lines in one
    string,** and an empty string sends none, as an empty body does.
23. **A token wait inside `block_on` is a panic:** "a task waits for JS,
    as `fetch` does, and JS cannot answer while block_on holds the thread;
    await it from an `async fn main` instead" (`a_fetch_in_block_on_panics`).
    And `block_on` from a task is re-entrant wherever the task runs: the
    check reads the poll in progress too, since a task a click spawned runs
    in the click's turn, where no loop has set 4.1's flag
    (`block_on_in_a_task_a_click_spawned_panics`). The spec leaves
    `block_on` open.

### The fake DOM and the tests

24. **The fake DOM has no focus and no blur;** nested calls come from
    `click()`. `std/dom` has no way to focus an element, so a blur on
    removal could not be reached. Spec §9 lists "a blur when a focused
    element is removed".
25. **The fake DOM's events are its own `Target`, not Node's
    `EventTarget`,** where spec §9 names Node's. Node's reports an
    exception a listener throws as an uncaught error, which would end the
    harness; the fake keeps it, in `uncaught`, as a browser reports it and
    goes on, and decision 4's `ended` check then stops the outer handler.

+# ADR 0041 — `std/dom` and the boundary with JS
+
+## Status
+
+Accepted, 2026-10-16 (Phase 4.2, branch `claude/loving-archimedes-frtf5q`;
+spec `docs/superpowers/specs/2026-10-16-phase-4-2-std-dom-and-the-shim-design.md`).
+`extern "js"`, the handles' release by the collector, `fetch` as an
+`async fn`, and `import dom` are the user's decisions of 2026-10-16.
+
+## Context
+
+After 4.1 a WASM build ran the whole language, but nothing in it could
+touch a page, and JS could not call it.
+- ADR 0038 said `std/dom` would reach the shim through compiler-known
+  functions. Each such function so far had meant a `Builtin`, an
+  `RtFunc`, a signature in the checker, and a shim entry.
+- `nova-spec/30-FRONTEND.md` §9.3 passes JS objects by handle and
+  functions by a "trampoline via stable function pointer", but says
+  nothing of when a handle is released or what keeps a function JS holds
+  alive.
+- ADR 0040's collector runs only at the end of a turn, and its roots were
+  the executor's tables and tasks. A closure only JS holds was in none of
+  them.
+- Every std module was in every program's prelude.
+
+## Decision
+
+1. **std declares JS functions as `extern "js"`.**
+   - Only a std module of a WASM build may: a user's `extern` block is
+     still E0090 on WASM, and `"js"` is still E0900 natively.
+   - Parameters and results are `Int`, `Float`, `Bool` and `String`.
+   - The backend imports each called one from `env` under its name; the
+     shim holds each one's JS and adds only those the module imports.
+   - A JS exception in one is a Nova panic that names the function.
+   - User code still has no JS interop: `@js_import` and `@js_export`
+     stay in ADR 0038's backlog.
+2. **JS objects are handles, released by the collector.**
+   - The shim keeps the objects in a table; Nova holds a slot's index in
+     a 16-byte box, whose address a record keeps in an `Int` field. The
+     collector is conservative, so that field keeps the box.
+   - A weak registry of boxes, in `std/rt`, is walked after each sweep, as
+     the task index is pruned: a freed box's slot is released.
+   - A slot that holds nothing is a panic. A box is freed only once no
+     value holds it, so no value names a released slot; a value built by
+     hand reads whatever word its address holds, and reaches at most an
+     object of the program's own table.
+3. **Closures JS may call are a root, and each call from JS is a turn.**
+   - `std/rt` keeps a table of `fn(Int)` closures, whose entries the
+     collector marks. `std/dom` wraps each handler in one.
+   - `nova_call` calls an entry, then runs a turn: it wakes what is due,
+     runs the queue, and collects if a collection is due. A call made
+     while Nova code is on the stack (a handler that clicks another
+     element) runs its handler only: the shim counts the calls in
+     progress, and only the outermost runs the turn, so the collector
+     never runs with a Nova frame on the stack.
+   - A module that registers such a closure exports `nova_call`, and the
+     turn and the switches with it, so a program with a synchronous `main`
+     collects at the end of each call.
+   - A listener's closure stays a root until the listener is removed.
+   - A task that calls `block_on` panics as re-entrant wherever it runs,
+     in a call's turn as in an `async fn main`'s.
+4. **A task can wait for JS.** It parks on a token, a handle the shim
+   settles: `fetch` settles one with its reply, then calls `nova_wake`,
+   which queues the tasks parked on it and runs a turn. A turn whose only
+   waits are on tokens returns -2, and JS sets no timer. Inside
+   `block_on`, which holds the thread, such a wait is a panic.
+5. **`std/dom` is std's first imported module.** It is in WASM's std but in
+   no prelude: a program writes `import dom`. Natively that import is
+   E0092. The names `dom` and `ui` are std's: a project's module under
+   either is E0093, and `nova-pm` refuses either as a package name.
+   `std/rt`'s public names are seen by std's modules only.
+6. **Tests use a fake DOM; CI uses Chromium.** `tests/dom/fake_dom.mjs` is
+   plain JS that holds what a browser holds and no more, so a missing root
+   shows under `NOVA_GC_STRESS`. A CI job, `browser`, clicks the gate's
+   counter in Chromium through Playwright, which only that job installs.
+
+## Consequences
+
+- **Adding a DOM function** is an `extern "js"` declaration and a wrapper
+  in `std/dom`, and an arm in `shim.rs`'s `js_function`: no new `Builtin`,
+  `RtFunc` or signature in the checker.
+- **Handles and closures are the collector's,** so 4.3's reactive graph,
+  whose effects JS calls back, needs no new mechanism.
+- **Every shim carries the scheduler,** about 0.5 KB gzipped: hello world's
+  `app.js` is 2.8 KB where it was 2.3 KB.
+- **An `async fn main` imports `host_release`,** because the collector may
+  release handles, so its shim carries the handle table too: about 0.7 KB
+  more.
+- **The fake DOM can differ from a browser.** The browser job is the
+  check, and later sub-phases add their own browser tests.
+
