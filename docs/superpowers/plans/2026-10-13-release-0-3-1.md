# `0.3.1`, the extension's rename, Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `v0.3.1` is published, with the VS Code extension in the
Marketplace and Open VSX as `sakeerin.vscode-nova`. A release pull
request renames the extension, corrects the texts and bumps the version;
then the runbook's steps run, each on the user's word; then a records
pull request says what happened.

**Spec:** `docs/superpowers/specs/2026-10-13-release-0-3-1-design.md`,
approved by the user on 2026-10-13. Its §9 lists the decisions.

**Runbook:** `docs/releasing.md`. This plan does not repeat its steps; it
says which of them the agent runs, with what, and what it checks.

## Global Constraints

- **Every [stop] waits for the user's explicit word in this
  conversation.** That covers every [stop] in the runbook and every step
  marked [stop] in the spec's §4 and §5. A word given for one step does
  not cover the next.
- **`Cargo.lock` changes only in Task 3, by `cargo update --workspace`:**
  23 lines, the workspace's own packages. Any other change stops the
  task.
- **The rules carried from earlier sub-phases:**
  - MSRV 1.78, with no `Option::is_none_or`;
  - no new crate;
  - no change to `nova`'s code.
- **Tests never touch the internet.**
  - The two tests Task 1 extends read files in the repository.
  - A run that needs `$NOVA_HOME` sets it to a fresh directory with a
    fixed name.
- **No secret is read, printed or stored by the agent.** The crates.io
  token and the store tokens are the user's, typed by the user into
  GitHub or their own terminal.
- **The merge and the PR body.**
  - Merge by rebase, on the user's word; never enable auto-merge.
  - PR bodies hold no local paths and no personal name. `Sakeerin`
    appears only in repository URLs, and `sakeerin` only as the publisher
    ID.
- **This machine is Linux;** Windows and macOS results come from CI.

## Conventions

- **Commits.** One commit per task, each message ending with the
  session's two attribution lines.
- **Before each commit:** `cargo fmt --all -- --check` and the named
  tests.
- **When a result differs from an `Expected:`,** fix it in the smallest
  way, and record it as a ruling, with its cost if wrong, in the ledger
  (`$P/ledger-031.md`, `$P` being the session's scratch directory).
- **The release commit stays the PR's last commit.** The runbook's step 1
  asks for "a pull request whose last commit is the release commit", and
  its step 2 tags that commit.

### Task 5: The release (spec §4 and §5)

The agent's part, step by step. Each **[stop]** first gets the user's
word.

- **Step 0, before Task 3's commit is pushed.** The user's Marketplace
  check of `vscode-nova` must have found the name free. If it was taken,
  stop: the user picks a name, and Tasks 1 to 3 use it.
- **Step 1.** On the word:
  - merge Task 4's PR by rebase, pinned to its head
    (`merge_pull_request`, `merge_method: rebase`, `expectedHeadSha` the
    head);
  - check that the merged tree equals the head's;
  - read CI on `main`.
- **Step 2. The tag.** The user makes and pushes it, with these
  commands, given in full:

  ```sh
  git fetch origin main
  git log -1 --format='%H %s' origin/main    # release: v0.3.1, the extension as sakeerin.vscode-nova
  git tag -a v0.3.1 -m "Nova v0.3.1" -m "The VS Code extension as sakeerin.vscode-nova, in the Marketplace and Open VSX." "$(git rev-parse origin/main)"
  git push origin v0.3.1
  git ls-remote --tags origin v0.3.1
  ```

  The last line must print the tag. The agent then reads:
  - the Release run's jobs;
  - the release, through `get_release_by_tag` with tag `v0.3.1`: eight
    assets and `SHA256SUMS`, not a draft, not a prerelease, its notes the
    `[0.3.1]` section;
  - `get_latest_release`, which must name `v0.3.1`.

  The runbook's download and `sha256sum --check` are the agent's if the
  sandbox reaches the assets, else the user's.
- **Step 3. crates.io.**
  - The user makes the token and adds the secret, and says so.
  - On the word, the agent starts "Publish to crates.io"
    (`actions_run_trigger`, `method: run_workflow`,
    `workflow_id: publish-crates.yml`, `ref: v0.3.1`,
    `inputs: {"version": "0.3.1"}`), then finds the run with
    `actions_list`.
  - The user approves the deployment.
  - Expected:
    - the owner check prints the 19 crates as `on crates.io, owned by
      Sakeerin`;
    - the 19 uploads finish within minutes, inside the burst of 30.
  - When the run ends, whatever the result, remind the user to revoke the
    token and delete the secret.
- **Step 4. The extension.** The user publishes `nova-vscode-0.3.1.vsix`
  to both stores (the runbook's step 4), and says what the listings show.
- **Step 5. "Release gate".** On the word, the agent starts it the same
  way (`workflow_id: release-gate.yml`, `ref: main`,
  `inputs: {"version": "0.3.1"}`) and reads its six jobs. It needs
  nothing from step 4, so if step 4 waits, ask the user whether the gate
  goes first.
- **Step 6. The user's store install** (spec §5). The user sends:
  - the screenshot of completion;
  - the `--list-extensions` line;
  - `nova version`'s three lines.
- **If a step fails:** apply the runbook's §7 and the spec's §7. Tell the
